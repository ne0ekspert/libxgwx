## Coordinate findings

Native element and wire records store Y as **three little-endian bytes**, with
four coordinate units per physical row. Native XGK row 65 uses `04 01 00` (260),
and IEC L16384 uses `00 00 01` (65536). XGK coordinates use u32 throughout the decoder, writer and WASM interface and
serialize all three bytes. IEC framing still rejects the third nonzero byte.

The stored program row-count field has an extended representation at 65535:
`ffff` followed by a little-endian u32 count, then the u16 group count. This adds
four bytes to the program header. The L65535 fixture stores count 65536 and five
groups. The XGK writer handles both header sizes and rejects growth beyond 65,535
physical rows (indices 0 through 65534).

The local `XG5000_Manual_V3.1_202510_KR.pdf`, PDF page 209, printed section 5.1,
lists 65,535 editable lines and 31 contacts per line for the legacy LD editor.
This is a documented editor limit, not native validation of every CPU or shape.
The generated XGK boundary project at row 65534 opened and passed Check Program
with zero errors and warnings, survived Save As byte-for-byte, and reopened at
the correct physical row. This validates sparse contact/coil programs at that
boundary; wider branch/function shifts are covered by local codec tests.

No hard IEC maximum has been established by these probes; L65535 is the highest
native-created, checked and saved row tested here. The L65535 and XGK row 65
files were also reopened in XG5000 at their correct positions; the reopened
L65535 project passed Check Program again with zero errors.
